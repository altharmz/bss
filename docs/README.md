# bss documentation

Documentation of what is **built** in bss, for a technical reader new to the project and
for demos. Every behavioural claim names the code that implements it and, where one
exists, the test that proves it. Anything planned but not built is marked **planned**;
the source for status is [progress/scope.yaml](progress/scope.yaml) and the generated
[PROGRESS.md](PROGRESS.md). The project's working rules - for humans and for the coding
agent - stay in [CLAUDE.md](../CLAUDE.md), the decisions and their rationale by area in
[decisions/](decisions/README.md); these pages summarise and link to them.

## Reading order

1. [overview.md](overview.md) - what bss is, its scope, the TMF APIs and versions, the
   runtime architecture on the VPS, authentication and configuration.
2. [domain.md](domain.md) - the TM Forum SID model as implemented: entities,
   lifecycles, catalog invariants, ordering, the billing rules, clock and time zone.
3. [billing-worker.md](billing-worker.md) - the daily billing run (stage 4): schedule,
   ownership and takeover, per-account outcomes, failures and backoff, catch-up, retry,
   status flips, the request queue, `/billing-status`, liveness, signals.
4. [ui.md](ui.md) - the admin console's screens and actions and the API operations each
   one calls; the planned Billing runs screen.
5. [operations.md](operations.md) - local development, tests (incl. cloud sessions),
   deploy and its checks, backups, monitoring, the agent harness.
6. Reference, generated from the code:
   - [api/](api/README.md) - one page per API: operations, parameters, request and
     response schemas, the `BssBillingAccount` extension, deviations, errors;
   - [db/](db/README.md) - the schema at migration head: ER diagrams by area, one page per
     table (columns, constraints, indexes, foreign keys), enums.
7. [archive/doc-findings.md](archive/doc-findings.md) - where code and documentation disagree, untested
   behaviour, open points.

## Generated vs hand-written

`docs/api/` and `docs/db/` are generated by `make docs` (`tests/docs_collect.py` in the
app container, then `scripts/docs/generate.py`) - never edit them by hand.
`make docs-check`, part of `make verify`, regenerates them and fails if the committed
pages differ. The hand-written parts of the API pages live in
[`scripts/docs/api-notes/`](../scripts/docs/api-notes/); table and column descriptions
are `COMMENT ON` statements in the migrations (`alembic/versions/0005_schema_comments.py`).
The generator fails when an operation has no match in its spec, or a table has no
comment, so the reference cannot silently fall behind the code.
