# Usage records and allowance tracking (issue #190, epic #182)

Usage from the network is stored per line and compared with the plan's allowance, so agents
see usage and the system can react to thresholds. Caps and throttling stay on the network;
the plan allowance rating of this slice is none (included usage); pay-as-you-go rating is
the second half of this file (#191). Design approved by the human's
standing delegation (decided following TMF). The UI half is issue #216 (190b).

## TMF635 (vendored v5.0.0, base `/tmf-api/productUsageManagement/v5`)

Implemented: `GET /productUsage`, `GET /productUsage/{id}`, `POST /productUsage` (idempotent
by `externalIdentifier`; a replay answers the stored usage again with 201, because the spec
declares no 200). Not implemented, by decision: PATCH and DELETE (405: a usage is a fact the
network reported), `exportJob` and `/hub` (the spec's only events are the export job's;
ProductUsage has none), TMF767 usage specifications (`usageSpecification.id` is a fixed kind:
`data`, `voice`, `sms`). `serviceUsage`, `relatedParty`, `usageProductPrice` are 422 on POST.
Status: `notRated` (matched), `rated` (a pay-as-you-go line's, below) or `rejected` (`noLine`). Tests validate against
the vendored schemas (`tests/apiclient.py` `NO_HUB`).

## Data (migration 0058)

- `usage_record`: `network_record_id` UNIQUE (the network's record id is the idempotency key),
  `kind`, `quantity` (data bytes, voice seconds, sms messages), `roaming`, `throttled` (as
  reported), `msisdn`/`imsi`, `event_at`, `event_date` (business date in `BILLING_TZ`),
  `product_id`/`billing_account_id` (null when unmatched), `status`.
- `usage_threshold`: PK (product, period start, allowance, threshold 80|100). The insert is
  the once-only guard and the durable event the notifications slice (#192) reads. These are
  not TMF events (the spec has none).

## Feed

`NetworkAdapter.usage_records(limit)` returns unacknowledged records, `ack_usage(ids)` confirms
them after the commit. `app/worker/usage.py` runs in every prepaid dispatch after the ports:
batches of 500, each in one transaction (`ON CONFLICT DO NOTHING`) followed by its
acknowledgement, so a lost acknowledgement resends records that are stored once. A wake-up
takes batches until one is not full (the feed is empty), an acknowledgement fails, a stop is
asked for, or 120 s have passed (`FEED_BUDGET`); the rest waits for the next wake-up.

A batch is stored by `ingest_batch` (`app/network/usage.py`): the known ids, the lines,
the insert, the plan periods, the profiles and the period totals are one statement each
for the whole batch, and the result is what `ingest` gives record by record (a test stores
the same batch both ways and compares rows and thresholds). TMF635 POST keeps `ingest`.
Why (#281, measured on the 100k dataset at the load-test target of 2M records a day, 23/s
average and 70/s peak): one batch per wake-up is at most 8.3 records/s, and the feed fell
47 min behind; taking batches until the feed is empty was still only 80-125 records/s,
about seven statements per record, so the worker spent its whole wake-up on the feed and
fell 19 min behind at 70/s. Stub: `inject_usage(...)`, nothing
is generated by itself. No new setting.

## Matching

By MSISDN, else IMSI, through `number_assignment` valid on the event date (cancelled claims
ignored): a record from before a number change maps to the product that held the number then.
A record no line held is stored `rejected` / `noLine` and counts for nobody. TMF635 POST names
the product and skips matching.

## Allowance

Period = the `funded_interval` covering the event date (latest grant when a mid-period change
left two; an offering change starts a new period). No grant (postpaid, or not covered): usage is
stored, no period and no allowance. Included = the profile the network was last told for the
product (latest confirmed `activate` / `change_profile`, else the offering's effective profile):
`dataAllowanceMb` (x 1 MiB), `voiceMinutes` (x 60 s), `smsCount`; 0 means nothing included and
no thresholds. Add-ons (#187) send `change_profile` with the raised allowance, so they are
included without this slice knowing them. 80% and 100% are noted per ingested record of the
kind (`used*100 >= included*pct`), once per product, period and kind (a record can pass both).
**Throttled** = the period's latest record says so, or data used reached `dataCapMb`.

## Usage zones (2026-11-16, issue #200)

A record is in one zone: **roaming** when the network says `roaming`, else **international**
for a voice or SMS record to a non-US destination (`usage_record.international`, migration
0084: the TMF635 `usageCharacteristic` `international` on POST, the feed record's field), else
**domestic**. Each zone counts only against its own allowance: domestic as before
(`dataAllowanceMb`, `voiceMinutes`, `smsCount`), roaming against `roamingDataMb`,
`roamingMinutes`, `roamingSmsCount`, international calls against `internationalMinutes`
(international SMS and data have no allowance of their own). **A change:** before this slice a
roaming record counted against the domestic allowance; now it does not. A record in a zone with
no allowance is stored and counted with `included = 0`: no threshold. The 80% and 100%
thresholds are per zone (`usage_threshold.zone`, existing rows domestic); a domestic
notification keeps its old dedupe key, the others add the zone. `ingest` and `ingest_batch`
stay equal (the test stores one batch both ways). The summary lists the domestic pools always
and a roaming or international pool when it has an allowance or usage, each with its `zone`.

## Internal API

`GET /internal/v1/usage/summary?product.id=[&date=]` (ours; also an MCP tool): period, per kind
used / included / remaining / percent / thresholds, throttled. Records are listed through
TMF635.

## Not in this slice

UI (#216), TMF635 export jobs and hub. The threshold notifications (#192) are done: see
[notifications.md](notifications.md).

# Pay-as-you-go rating (issue #191, epic #182)

Pay-as-you-go lines pay for usage from the money balance, rated from the usage records, and
are barred on the network when the balance runs out. Plan lines ignore usage prices (included
usage only), and their records stay `notRated`. Design approved by the human's standing
delegation (decided following TMF, the issue comment). The UI half is issue #220 (191b).
Migration `0060`; no new setting.

## Usage prices (TMF620)

`priceType: usage` (TMF635 names it among the price types: "recurring, one time and usage") on
a `payAsYouGo` offering only; on a plan or add-on offering it is a 422, and an offering with
usage prices cannot change its kind. The price is that of **one block** of the TMF620
`unitOfMeasure` Quantity `{amount, units}`, required (422): the unit gives the kind and the
**rounding unit** (data `KB` `MB` `GB`, voice `second` `minute`, sms `message`; the block is a whole number of
bytes, seconds or messages). So `0.10 USD` per `{amount: 1, units: MB}` charges data in whole
MB. Stored as `usage_kind` and `usage_block` beside the document (migration 0060); the
no-overlap rule is per offering, kind and currency, so data, voice and SMS prices coexist.
The type and the unit never change by PATCH (422 / 409: attach a new price). Prices are
`numeric(12,2)`, so the cheapest block is 0.01.

## Rating (the design gate: a daily aggregate)

`app/billing/usage_rating.py`, run each worker tick by `app/worker/rating.py`. Only **closed
days** (event date before today in `BILLING_TZ`) are rated, so a day is never rounded twice. The
unrated records of a pay-as-you-go line (product `grantless`, no plan parent, offering kind
`payAsYouGo` on the event date) are grouped by line, event date and kind, **summed, rounded up
once to whole blocks** and charged `blocks x price`, the price being the offering's usage price
valid at midnight of the event date in the account's currency. A group without a usage price
(or at price 0) is rated with no charge. A late record of an already rated day is a group of
its own in the next pass (known limit: its rounding is separate). Not real-time: the balance
moves, and the line is barred, after the day closes.

Each group is one `oneTime` ABR (TMF678 `appliedBillingCharge`, `charge_name` = the price's name,
`one_time_price_id` = the usage price, period = the event day), taxed through the tax adapter
as `usage` (committed in the same transaction with its `tax_transaction`; without a service
address the price's flat tax), all of a pass on one **off-cycle bill** (the fee pattern),
issued and settled against the account's unused payments at once (`settle_account`). The
ledger is payments less ABRs, so the charge draws the balance down by itself.

A pass is a retained `prepaid_command` of kind `usage` (id = uuid5 of its first record) with its
own run, posted under the account lock in one transaction: all of it or nothing (a tax engine
outage leaves the records unrated; the next tick retries). `usage_charge` (primary key = the
record) is the once-only guard and links record, pass, price and ABR; the pass revalidates the
records as unrated under the lock, so the feed resending, TMF635 POST replaying or the worker
running twice never charges twice. A record becomes TMF635 `rated`, with
`usageProductPrice` (the price of one block without tax, `dutyFreeAmount`, its unit).

**Zone prices (issue #200):** a usage price may name its zone in TMF620 `prodSpecCharValueUse`
`usageZone` (`domestic` by default, `roaming`, `international`; stored as
`product_offering_price.usage_zone`, only on a usage price, never changed afterwards: 409). The
no-overlap rule is per offering, kind, zone and currency. Rating groups by line, day, kind
**and zone**; a zone with no price of its own is rated without a charge, so **operators must
define roaming and international prices to charge them**.

## Negative balance and top-ups

What the balance cannot pay stays an **open bill**: the next payment settles the account's open
bills oldest first before anything else (`settle_account`, called by every payment path), so
the debt is recovered from the top-up and the balance after it is the top-up less the debt.
The balance may therefore be negative (internal `balance`, TMF654 `remainingValue`).

## Barring

Each tick (`app/billing/usage_bar.py`), after rating, every active pay-as-you-go line of a
prepaid account is compared with the account's spendable balance (ledger less holds): at zero or
below and not barred, a `suspend`; above zero and barred (and not suspended by an operator), a
`restore`. The commands are `usage_bar` rows (one per command, numbered per product; the latest
is the line's state), sent through the network adapter with the id as idempotency key and the
retry backoff of the order commands (never exhausted: temporary errors retry every hour at
most). A refusal is final and recorded (`refused`, nothing is repeated); a line that ended before
its command was sent has it `cancelled`. Own table, so order commands, the order gate and the
lifecycle slice (#188) stay untouched. A balance that a top-up leaves at zero or below keeps the
line barred. Internal `GET /internal/v1/usage/summary` carries `payAsYouGo` for such a line
(balance, `barred`, the last command's state, unrated records); null for any other line.

## Deviations and limits

- Rating waits for the day to close (daily aggregate), so zero-balance barring lags usage by up
  to a day, as the issue allows ("not real-time").
- Money moves through bills settled from payments; an adjustment or incoming transfer credit
  lowers the balance the same way but leaves the bill open until a payment arrives (the ledger
  is right either way).
- TMF635 PATCH, export jobs and hub stay out (usage.md above).

## productUsage lists need a line (2026-11-09, #286)

A deliberate deviation from TMF635, approved by the human for the load-test programme.
`GET /productUsage` without `product.id` or `id` is a 400: "productUsage list needs
product.id or id". A list across every subscriber is not a use case (the UI and MCP always
list per line), and at 2M records a day counting it would read the whole table. Per line
it is bounded (about 600 records a month) and served by `usage_record (product_id,
event_at DESC, id)` (migration 0070). Rejected records have no line; they are read by
`id`.

## Partitions (2026-11-11, #282)

Approved by the human on 2026-11-09 for the load-test programme: at 2M records a day
`usage_record` grows by about 730M rows a year. Migration `0076`.

- **Monthly range partitions on `event_date`** (`usage_record_yYYYYmMM`). The primary key is
  `(id, event_date)`. Reading one record by id probes each partition's key index.
- **Idempotency:** `UNIQUE (network_record_id, event_date)`. A resend carries the same
  `event_at`, so the same date, and the unique key catches it. `ingest` first looks the id up
  through the plain index `usage_record_network_record_idx`. A record id that comes back
  with another date is a replay: the stored record is answered (TMF635 POST) or skipped
  (the feed), as before. **Accepted race:** two concurrent first inserts of one id with
  different dates can both be stored. `by_network_id` then answers the first stored.
- **No foreign key to `usage_record`** from `usage_charge.usage_record_id` or from
  `usage_threshold.usage_record_id`. The columns stay, so an old partition can be dropped
  while its charges (billing evidence) stay. The issue named `usage_charge`; the threshold's
  key had the same problem (a foreign key to a partitioned table must include the partition
  key, and it would forbid the drop), so it went the same way.
- **Retention:** a partition whose month ended 13 months before the current month began is
  dropped (`DROP TABLE`: instant, nothing to vacuum). On 2026-11-11, September 2025 goes and
  October 2025 stays. Rated amounts survive in `usage_charge` and the ABRs. A drop waits at
  most 5 s for the table's readers, else it is tried at the next wake-up.
- **Made ahead:** the housekeeping calls `usage_record_partition(month)` (a database
  function from migration 0076) for the current and the next two months every day. It
  is idempotent. A `DEFAULT` partition is the safety net of a missing month. Its row count is
  the `/metrics` gauge `bss_usage_record_default_rows`, with the alert
  `BssUsageDefaultPartition` when it is above 0. A partition made for a month that the
  DEFAULT partition already holds rows of takes those rows over: it is built beside the
  table, the rows move in, then it is attached.
- **Autovacuum per partition:** Postgres refuses storage parameters on a partitioned table
  ("cannot specify storage parameters for a partitioned table; specify storage parameters for
  its leaf partitions instead"), so the issue's "set on the parent, inherited by new
  partitions" cannot be done as written. The same settings are set by
  `usage_record_partition` on every partition it makes, and on the DEFAULT partition.
- **The conversion** ran in the migration's one transaction: a new partitioned table,
  partitions for every month from the oldest record to two months ahead, the copy, then the
  keys and indexes (built once per partition after the copy), the drop of the old table.
  Measured on the 100k dataset (6.8M records, `lt-db` on cpuset `4-7`): upgrade 493 s,
  downgrade 921 s. Production holds far fewer records today.
